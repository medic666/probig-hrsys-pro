## 企业人事与行政资产管理系统
你是一位精通全栈开发的高级工程师，请按照以下要求，为我构建一个“企业人事与行政资产管理系统”生产级项目。要求单文件部署，结构清晰、可扩展、鲁棒性强。

### 技术栈参考
- 后端：Go, Gin, GORM, SQLite
- 前端：Bun, Vite, Vue3, TypeScript

### 数据库结构参考
**注册层**：注册类型有人员/组织
**文件层**：后台上传并在数据库中登记文件。
**事件层**：事件层是本管理系统的核心驱动。
   - **人员事件**：用于增删改人员的(姓名\考勤组\入职日期\基本工资\绩效工资\计薪天数\职位津贴\餐补\房补\交通补贴\高温补贴\保险补偿\公积金补偿\社保代扣\公积金代扣)等职务信息，以及电话(多个)\电子邮箱(多个)\身份证号\性别\生日\民族\籍贯\住址\银行卡号(多个)\政治面貌\婚姻状态\别名等基础信息(以上信息有多条可以用json字段储存)
   - **组织事件**：用于增删改组织的(公司名称/统一社会信用代码/地址/联系电话/开户行/银行账号/营业执照(唯一文件ID)/公章(唯一文件ID))等信息。
   - **假勤事件**：关联人员，可单独添加假勤事件(或者从打卡记录文件批量导入打卡事件,导入文件模板和解析逻辑我们后续再完善)，事件记录每日出勤事件(类型分普通出勤、补班出勤)、休假事件(调休、事假、病假、年假、法定假、福利假)、加班事件(工作日加班、节假日加班)、违纪事件(缺卡、迟到、早退)、年假调整(年假配发、年假结转)。
   - **工资事件**：关联，包含业绩、奖惩、借款扣除、个税扣除等事件类型。
**关联层**：
   - **文件关联**：为人员/组织/事件添加附属文件关联。
   - **事件关联**：为人员/组织添加事件关联。
**时点快照层**：
   - **人员快照**：通过人员历史事件来递推在每个事件节点的人员总体信息。每次发生事件的增删改后，自动更新员工自事件生效日期到最新日期的整个快照链。
   - **组织快照**：通过组织历史事件来递推在每个事件节点的组织总体信息。每次发生事件的增删改后，自动更新组织自事件生效日期到最新日期的整个快照链。
**时段汇总层**：
   - **假勤汇总**：通过汇总一个时段内的假勤事件，记录时段内的总体假勤信息。每次发生假勤事件的增删改后，不自动更新汇总表。而是管理员手工点击考勤核算时，更新最新的汇总表。
   - **工资汇总**：通过汇总时段内人员每日的职务信息* 每日的假勤信息，推算出勤工资，再叠加工资调整事件如业绩、奖惩、借款扣除、个税扣除等，得出最后的工资汇总表。每次发生人员事件、假勤事件、工资事件的增删改后，不自动更新汇总表。而是管理员手工点击工资核算时，更新最新的汇总表。
**审计层**：所有对(注册层/文件层/事件层)的变动操作都要记录下来，payload里面保存完整的信息详情。审计日志只可查看不可操作删除。

### 前端需求参考
#### 模块划分
**人员管理**：展示最新人员快照，可增删查改人员信息。展示人员事件记录和历史版本，可增删改人员事件。
**组织管理**：展示最新组织快照，可增删查改组织信息。展示组织事件记录和历史版本，可增删改组织事件。
**假勤管理**：按时间/人员等维度展示假勤汇总，展示假勤事件。增删查改假勤事件。有考勤核算功能。
**工资管理**：按时间/人员等维度展示工资汇总，展示共咋子事件。增删查改工资事件。有工资核算功能。
**文件管理**：文件的列表查看，上传、调整关联、删除等功能。
**操作审计**：展示审计日志。
#### 其他需求
**用户与权限**：初始设定管理员角色，但需要预留 RBAC 模型，后续可扩展财务、老板等角色。权限控制到模块的“读、写、删”操作，前端根据权限动态展示菜单和按钮。
**功能齐全**：各模块应合理包含展示、搜索、筛选、操作、分页、数据导出等功能。

### 工资计算规则
- **日薪公式**：`日薪 = 基本工资 / 计薪天数`
- **出勤工资**：`（（普通出勤天数+补班出勤天数）*1+（调休+事假）*0+（病假）*病假补贴系数0.6+（年假、法定假、福利假）*1）*日薪`
- **全勤奖**：无事假时`（（普通出勤天数+补班出勤天数）*1+（病假）*病假补贴系数0.6+（年假、法定假、福利假）*1-违纪次数）*全勤奖系数10`
- **加班工资**：`（(基本工资+餐补)/计薪天数）*工作日加班天数*工作日加班系数1.5+（(基本工资+餐补)/计薪天数）*(节假日加班天数+年假结转)*节假日加班系数2`
- **绩效工资**：默认绩效系数为1，缺勤不扣绩效。
- **代扣项**：社保、公积金按个人职务信息中的数字计算，个税扣除按照工资调整事件进行加减。
- **幂等保证**：同一人同一月份多次计算结果一致
- **调整事件**：支持业绩、奖惩等工资调整事件，叠加入月度工资

### 后端需求参考
- **架构要求**：分层设计，事务处理写操作（事件表+业务表同时写入），优雅错误处理，统一响应格式。
- **部署**：最终编译成一个二进制文件，包含前端静态资源，SQLite 数据库自动创建。

### 注意
- 理清项目中的数据驱动逻辑：
   - 人员和组织是通过事件汇总形成时点快照来展示信息的。修改人员和组织的信息，底层逻辑是生成新的事件。而事件本身也是可以修改的。增删改事件后要同步更新此时点以及后续的所有快照链。
   - 假勤和工资是通过事件汇总形成时段汇总，时段汇总不能直接修改，但是假勤和工资事件是可以修改的，假勤和工资事件修改以后不自动生成新的汇总表，而是管理员做考勤/工资核算时再更新。
- 前端页面中，人员/操作人/组织等对象不要只显示ID，资料导出也是不要只显示ID，要显示名字。任何地方都避免裸露的json而是需要可视化的界面。更不要前端直接写表名，这样暴露了数据库结构了，不仅用户难以理解，别有用心的人还可以利用。（记住程序是面向用户的，请全面避免这种展示信息的谬误）
- **重要**：时刻记得架构优雅清晰，可拓展，鲁棒。

### 调试方法
* 开发模式：`cd frontend && bun run build && cd ..` `go run .`
* DEV模式：`DEV_MODE=true go run .`
它的原理是 internal/config/config.go:18 读取环境变量 DEV_MODE，当值为 "true" 时，internal/router/router.go:86-87 跳过嵌入前端文件的服务，只暴露 API。此时你需要再开一个终端窗口启动前端开发服务器：`cd frontend && bun run dev`然后浏览器访问 http://localhost:5173。
